# tetris-vla — 意思を持つテトロミノたちの PoC

落下中のテトリスのピース 1 個 1 個が、独立したエージェントである。
各ピースは **盤面スナップショット画像 1 枚だけ** を見て、自分がどこに収まるかを決める。
決められた時速で落ち続け、落下は止められない。
他のピースが何を考えているかは分からない — 見えるのは、スナップショットに写っている分だけ。

ローカル VLA (Vision-Language-Action) をその「頭脳」に差せるようにしてある。

```bash
git clone https://github.com/s8tv9mvcz9-code/tetris-vla && cd tetris-vla
```

**Python 3.10 以上が必要。** macOS 標準の `python3` は 3.9 系のことがあるので確認する
(3.9 だと install 時に `requires a different Python` で止まる):

```bash
python3 --version
```

3.10 未満なら Homebrew などで入れて、そのバイナリで venv を作る
(`brew install python@3.11` → `python3.11 -m venv .venv`)。

```bash
python3 -m venv .venv && .venv/bin/pip install -U pip && .venv/bin/pip install -e ".[dev]"
```

```bash
.venv/bin/python -m tetris_vla run --agent vla-mock --active 3 --ascii-every 40
```

**モデルのインストールは不要。** 既定のバックエンドはローカル VLM の挙動
(レイテンシのゆらぎ / JSON 崩れ / 拒否 / 範囲外出力) を模した mock で、そのまま最後まで走る。
実機で回す手順は [実機 (Ollama) で動かす](#実機-ollama-で動かす) に。

依存は numpy / Pillow / httpx だけ (テストに pytest)。

## 1. この PoC が実際に測っているもの

素直に読むと「ローカル VLA にテトリスを解かせる」課題に見える。しかし 3B 級の VLM に
10x20 の格子を正確に読ませるのは無理筋で、そこを主指標にすると PoC は「失敗」としか言えなくなる。

そこで問いを 2 段に分けた。

| 問い | 指標 | 結論 |
|---|---|---|
| **A. 同じピクセルを見て、VLA は探索ソルバの判断にどれだけ近づけるか** | 一致率 / regret / パース失敗率 | 腕前 (skill) に対してほぼ線形に改善。出力破損の影響のほうが大きい |
| **B. 各エージェントが個別に最適でも、全体はうまくいくのか** | 穴/個 / ライン / 収まり率 | **いかない。しかも個別最適であるほど悪化する** |

そして B のほうが、はるかに面白い結果になった。

### 中心的な発見

同じ Dellacherie 探索を頭脳に使い、同じピクセルを与えたまま、**同時落下数だけ**を変える:

| 同時落下数 | オラクル一致率 | 穴/個 | 宣言どおり収まった率 |
|---|---|---|---|
| 1 体 | 1.000 | **0.02** | 1.00 |
| 2 体 | 1.000 | 0.54 | 0.92 |
| 3 体 | 1.000 | 0.98 | 0.77 |
| 4 体 | 1.000 | **1.31** | 0.67 |

*(seed 5 本平均、`ablate --study concurrency`)*

**一致率は 1.000 のまま動かない。** つまり全ての判断が、その瞬間の盤面に対して個別最適である。
それでも穴は 65 倍に増える。頭脳の質は一切劣化していない。劣化したのは
「他人が何を考えているか見えない」という一点だけだ。

次に、頭脳をそのままに **意図の共有度だけ** を変える:

| 協調モード | 一致率 | 消去ライン | 穴/個 | 最終最高列 | 推論/個 |
|---|---|---|---|---|---|
| 自律 (通信なし) | **1.000** | 3.8 | 0.98 | 19.8 | 5.31 |
| A2A (予定地を共有) | 0.518 | 6.4 | 0.55 | 18.4 | 5.48 |
| 独裁 (一括指揮) | 0.578 | **12.2** | **0.04** | **4.4** | **4.77** |

*(active=3, seed 5 本平均、`ablate --study coordination`)*

**一致率が最も高いモードが、最も弱い。**
全員が同じ地形を見て同じ「最良手」を導くから、狙いが重なって潰し合う。
協調とは、参照解からわざと外れる能力のことだった。

### 3 つめ: 上位が間に合わなくても、下位が回っていれば完走する

ピンボール題材 (`scripts/pinball_demo.py`) で戦略層を実機の qwen2.5vl:3b に
差し替え、Apple M2 / 8GB で走らせた実測:

| | 値 |
|---|---|
| VLM 推論 1 回の実時間 (中央値) | **374 秒** |
| デモ 1 回のゲーム内時間 | 29.9 秒 |
| 比 | **12.5 倍** |
| 同じ機材・短いプロンプト (テトリス/パラシュート) | 2.5 秒 |
| それでもスコア | **950 / 1000** (24/24、均等性 1.0) |

当初はこれを「上位が失速しても下位が回したから 950 点」と読んだ。**それは誤りだった。**

シミュレータには陳腐化の上限 `max_drift_ticks=30` があり、374 秒の推論が
**「0.60 秒古い助言」として扱われていた** (本来の陳腐化は 18,700 tick 相当で、
上限の 623 倍)。つまりあの 950 点は、実質新鮮な助言をもらって出した点数で、
遅さへの耐性を何も示していなかった。

陳腐化が実際に効くかを 12 seed で測ると、効く。ただし既定値がちょうど効かない
領域にあった:

| 助言の古さ | 点 |
|---|---|
| 0.0 秒 | 667 |
| **0.6 秒 (旧既定)** | **664** |
| 2.0 秒 | 475 |
| 8.0 秒 | 458 |

そこで `slowmo` を上げて実時間を tick に落とし、上限で隠さずに測り直した
(seed 0、6000 tick、VLM 600 tick 毎):

| | 終了 tick | 点 | 崩し | 均等性 | 命中 |
|---|---|---|---|---|---|
| ヒューリスティック・新鮮 | 6000 (完走) | **827** | 23/24 | 0.75 | 23 |
| ヒューリスティック・141 tick 古い | 2423 | 770 | 21/24 | 0.75 | **5** |
| **実機 qwen (141 tick 古い)** | **1298 (全滅)** | **540** | 19/24 | **0.25** | 6 |

損失が 2 つに分解できる。

**遅さの代償は「実行できないこと」。** 助言が 2.8 秒古いだけで命中が 23 → 5 に落ち、
面が 6000 tick 完走から 2423 tick で終わる。狙う先が分かっていても、
その頃には球がそこにいない。

**中身の代償は「配らないこと」。** qwen は 3 回とも「セグ 3」と答え続けた。
列ごとの消化は `[4,4,1,2,4,4]` (均等性 0.25) で、対照の `[4,4,4,3,4,4]` (0.75) と違い
工程を配分しない。同じ陳腐度で比べて 770 → 540 なので、
**この題材では遅さより助言の中身の方が高くついた。**

下位が回り続けること自体は本当で、qwen 走行でも 19/24 は崩れている。
だが「上位が失速しても平気」ではない。**下位が守れるのは工程が止まらないことまでで、
何を優先するかを外すと数字は落ちる。**

原因は常駐メモリで、qwen の常駐が 3.7GB → 5.6GB に膨らみ空きが 6% に落ちた時点で
推論が秒から分のオーダーへ落ちた。

当初は「文脈長に対する KV キャッシュ確保が犯人」と考えていたが、**冷えたマシンで
`--num-ctx 2048` を測って否定された**:

| | ベースライン | num_ctx=2048 |
|---|---|---|
| 画像 | 144x192 | 同じ |
| num_ctx | 既定 (≥4096) | **2048** |
| 常駐 (`ollama ps`) | 5.6 GB | **5.5 GB** |
| VLM レイテンシ | 343〜409 秒 | 278 / 347 / 369 秒 |

文脈長を半分以下にしても常駐は 0.1GB しか動かず、レイテンシも変わらない。
このとき swap が 3GB 使われていた。**犯人は文脈長でも画像面積でもなく、8GB の機械に
5.5GB 常駐のモデルを載せたこと自体**で、そこから誘発されるスワップが秒を分に変えている。

補足として、この測定の 1 回目だけは 30 秒で返っている。まだスワップが始まっていない
からで、**「冷えていれば速い」だけ**。2 回目以降はベースラインと区別できない。

→ 詳細は [docs/physical-ai-realtime.md](docs/physical-ai-realtime.md)。
図は `results/pinball_vlm.html` — VLM の助言・シーケンサ状態・盤面の事故・工程消化を
同じ時間軸に 4 段重ねてあるので、上位が沈黙している間に下位が走り切ったのが読める。

## 2. 途中判断を並べて見る

スコアのグラフは「どちらが勝ったか」しか教えてくれない。この PoC で見たいのは
**同じ盤面を見せたときに各方式が何を選んだか** なので、判断そのものを突き合わせる:

```bash
.venv/bin/python -m tetris_vla compare --seed 1 --active 3 --scenes 4 --out results/decisions.html
```

`results/decisions.html`（自己完結の 1 枚、外部参照なし）と、同じ内容の端末出力が出る:

```
=== t=120 落下中 3 体 ===
  参照 (地形のみの最良手)   #3T->c4r0 #4I->c3r0 #5Z->c8r1   衝突3セル 参照相違0体 推論0回
  自律 (通信なし)         #3T->c4r0 #4I->c3r0 #5Z->c8r1   衝突3セル 参照相違0体 推論3回
  A2A (予定地を共有)      #3T->c4r0 #4I->c9r1 #5Z->c0r0   衝突0セル 参照相違2体 推論6回
  独裁 (一括指揮)         #3T->c4r0 #4I->c9r1 #5Z->c3r1   衝突0セル 参照相違2体 推論1回
```

自律は参照と完全に一致し (相違 0 体)、そのせいで 3 セルの衝突を抱える。
A2A と独裁は参照から 2 体ぶん外れ、衝突を 0 にする。
**「間違えること」が正解になっている**瞬間が、1 行で読める。

HTML では同じ盤面が方式ごとに並び、細枠 = 現在位置、塗り + 太枠 = 宣言した着地点、
赤 = 複数ピースが同じセルを狙っている衝突、として重ね描きされる。

## 3. アーキテクチャ

```
tetris_vla/
  engine.py     テトリスのコア。SRS 形状 / 7-bag / 重力 / lock / ライン消去。
                拡張点はただ 1 つ: 盤面に同時に N 個の落下ピースが存在しうる。
                純粋・決定的。wall-clock も I/O も参照しない。
  render.py     盤面 -> PNG と、その厳密な逆変換 (decode)。公平性の担保。
  agents.py     Intent / ペルソナ / Dellacherie 探索 / VLA + バックエンド / 独裁エージェント
  runtime.py    論理 tick クロック、単一サーバ推論待ち行列、反射コントローラ、JSONL ログ
  evaluate.py   比較実験とアブレーション研究
  benchmark.py  tier 制ハードルとスコアリング
  compare.py    途中判断の突き合わせと HTML 出力
  cli.py        run / eval / ablate / bench / compare / snapshot / replay / doctor
tests/          152 テスト
```

### 設計上の要点

**すべてのエージェントは同じピクセルしか見ない。**
`Observation` に含まれるのは PNG バイト列と自己情報 (自分の種類・信条) だけで、
盤面配列や `Engine` への参照は構造的に渡らない (`test_agent_receives_pixels_only`)。
ヒューリスティック baseline も、`render.decode()` で画像から盤面を復元してから探索する。
`decode(render(x)) == x` はランダム盤面 12 種 x セルサイズ 3 種で検証済み
(`test_render_decode_roundtrip_is_exact`)。**同じピクセル、違う頭脳** という比較が成立する。

**時間は論理 tick で進み、落下速度は交渉不能。**
「決められた時速」は設定値であって、VLM の返答が遅いかどうかとは無関係。
実測レイテンシは `service_ticks = round(latency_s / tick_seconds)` で tick に換算され、
**「答えが返ってくる頃には盤面が古い」**という遅延としてゲーム内に現れる。
tick 5 に撮ったスナップショットに対する答えが tick 13 に届けば、staleness は 8 tick。

**推論器は 1 台。**
8GB / モデル 1 インスタンスという現実に合わせ、推論は単一サーバ待ち行列。
3 個のピースが同時に判断を求めたら 2 個は待ち、その待ち時間も staleness に加算される。
`--workers` で増やせるが、ローカルでは 1 が現実的。

**エージェントは操舵しかできない。**
意図 `(col, rot)` を反射コントローラが 1 tick 1 アクションに落とす。落下は止められない。
反射層には「今その方向へ動けるか」の身体感覚だけを与えてあり (`Engine.action_is_legal`)、
塞がれていたら突っ込まずに待つ。この判定が実適用と一致することはテストで保証している。

**同時落下の lock 規則。**
確定地形か床に阻まれたときだけ lock する。**他の落下ピースに阻まれただけでは lock しない**
(でないと下のピースが退いたときに空中固定が残る)。ただし停滞が続いたら強制 lock して
デッドロックを断つ。

**「間に合わなかった推論」を必ず記録する。**
エピソード終了時に推論中だった要求も、答えが届いた時には既に lock されていた判断も、
別々のカウンタに残る。遅い VLA ではここが無視できない割合になる。

### 協調モード

| モード | 何が見えるか | 実装 |
|---|---|---|
| `autonomous` | 他ピースの**位置**だけ | 各ピースが独立に推論 |
| `a2a` | 他ピースの**宣言した予定地** | 宣言をゴーストとしてスナップショットに描き込む |
| `dictator` | 全ピースの意図 (同一人物なので) | 1 回の推論で全ピース分の割り当てを出力 |

A2A の通信は**画像の中だけで完結する**。宣言 `(col, rot)` はランタイムが着地セルに変換して
灰青のゴーストとして描き、エージェントはそれをピクセルとして読む。
「盤面スナップショットから見えている分しかわからない」という制約を字義どおり保ったまま、
意図の共有を導入できる。ゴーストは空セルにしか描かれないので、確定/落下ブロックの
厳密デコードは壊れない (`test_ghosts_decode_as_a_separate_plane_without_breaking_the_board`)。

### ペルソナ = 各ピースの「意思」

`neutral` / `flat` (平らに積みたい) / `nohole` (穴を極度に嫌う) / `left` / `right` /
`wellkeeper` (右端を I 用に空けておきたい)。

ペルソナは **ヒューリスティックの重みベクトルと VLA プロンプトの両方を同時に動かす**。
同じ目的関数を「探索で解く頭」と「言語で解く頭」に与えているので、両者の比較が意味を持つ。

## 4. 使い方

```bash
# 1 エピソード (mock VLA, 同時 3 体)
.venv/bin/python -m tetris_vla run --agent vla-mock --active 3 --ascii-every 40

# 協調モードを変える
.venv/bin/python -m tetris_vla run --agent heuristic --mode a2a --active 3
.venv/bin/python -m tetris_vla run --agent dictator-heuristic --active 3

# エージェントが実際に見ている 1 枚を書き出す
.venv/bin/python -m tetris_vla snapshot --out board.png --warmup 60

# 比較実験
.venv/bin/python -m tetris_vla eval --seeds 5 --out results

# アブレーション (coordination / coordination-vla / concurrency / perception / skill / latency / robustness)
.venv/bin/python -m tetris_vla ablate --study coordination --seeds 5 --out results

# マシンベンチマーク (3 モード比較)
.venv/bin/python -m tetris_vla bench --agent heuristic --modes autonomous,a2a,dictator --all-tiers --out results

# 途中判断の比較 HTML
.venv/bin/python -m tetris_vla compare --seed 1 --scenes 4 --out results/decisions.html

# 判断ログを残して後から読む / 決定的に再生する
.venv/bin/python -m tetris_vla run --agent vla-mock --log runs/a.jsonl
.venv/bin/python -m tetris_vla replay --log runs/a.jsonl
.venv/bin/python -m tetris_vla run --agent vla-replay --replay-log runs/a.jsonl

# テスト
.venv/bin/python -m pytest tests/ -q
```

### 実機 (Ollama) で動かす

**この環境には Ollama を入れていない** (数 GB のインストールになるため、判断は利用者に委ねた)。
実機で試す場合:

```bash
brew install ollama && ollama serve
```

```bash
ollama pull qwen2.5vl:3b
```

8GB のマシンなら 3B 級が上限の目安。7B 以上はスワップして極端に遅くなる。

```bash
.venv/bin/python -m tetris_vla doctor
.venv/bin/python -m tetris_vla run --agent vla-ollama --model qwen2.5vl:3b --active 2 --budget 2 --replan 20 --ticks 300 --log runs/real.jsonl
```

実機は 1 判断 1〜3 秒かかる。まず `--budget 2 --replan 20` で推論回数を絞ること。
`--log` を付けておけば、あとから `--agent vla-replay` で **決定的に** 再生できる
(生応答をそのまま食わせ直すので、実モデルを再度回さずに指標を取り直せる)。

## 5. マシンベンチマークとしての使い方

ゲームは論理 tick で進み、落下速度は固定。一方で推論時間は実測の wall-clock。
`tick_seconds` が **「このマシンに許される 1 手あたりの時間」** を定義する。

```
速いマシン → レイテンシが短い → 消費 tick が少ない → 判断が新鮮なうちに届く → 高スコア
遅いマシン → 答えが届く頃には盤面が変わっている → 待ち行列が伸びる → 低スコア
```

ゲーム側は一切忖度しない。1 秒遅ければ、その分だけ盤面は先に進む。

### ハードル (tier)

| tier | 同時 | 落下 | tick秒 | **1判断の許容時間** | 目標設置数 |
|---|---|---|---|---|---|
| T0 warmup | 1 | 8t/行 | 0.30 | **2.40s** | 15 |
| T1 easy | 2 | 6t/行 | 0.25 | **2.00s** | 20 |
| T2 standard | 3 | 4t/行 | 0.20 | **1.20s** | 25 |
| T3 hard | 4 | 3t/行 | 0.15 | **0.75s** | 30 |
| T4 extreme | 5 | 2t/行 | 0.10 | **0.40s** | 35 |

各 tier は「同じ数だけ設置し終えるまで」走らせるので、条件間で試行回数が揃う。

### スコア (0〜1000)

```
生存   0.35  設置数 / 目標数            — 天井まで積まずに走り切れたか
効率   0.30  ライン/個 ÷ 0.4 (理論上限) — 4セルで10幅の行を埋める上限が 0.4
無穴   0.20  1 - 穴/個 ÷ 1.5
制御   0.15  lock 時点で宣言どおりだった率
```

500 点で合格。1 tier 落とすと以降は未挑戦 (`--all-tiers` で全部走らせる)。

### 実測結果 (Apple M2 / 8GB, seed 3 本, 頭脳は Dellacherie 固定)

| 協調 | 最高tier | 合計 | T0 | T1 | T2 | T3 | T4 |
|---|---|---|---|---|---|---|---|
| autonomous | T2 | 3164 | 864 | 728 | 638 | 498 | 436 |
| a2a | T3 | 3531 | 864 | 883 | 750 | 677 | 357 |
| dictator | **T4** | **4079** | 864 | 890 | 852 | 866 | **607** |

T0 は同時落下 1 体なので協調の余地がなく、3 モードとも 864 で一致する (健全性チェック)。

**律速要因の自動診断がレポートに付く。** ヒューリスティックはレイテンシ比 0.01
(実測 3ms / 許容 1.2s) なので、これは**協調律速**であってマシン律速ではない。
つまり上の表は「CPU の速さ」ではなく「協調の難しさ」を測っている。
マシン性能が効いてくるのはレイテンシ比が 1.0 に近づいたとき — 実機 VLA を挿したときだ。

> **注意**: `--agent vla-mock` のレイテンシは合成値なので、モックでのベンチはマシンを測っていない。
> 本当にマシンを測るのは `--agent heuristic` (実 CPU 時間) と `--agent vla-ollama` (実推論時間) のみ。

興味深い副産物として、**A2A は T4 で自律より弱い** (357 対 436)。
極端に速い落下では宣言があっという間に陳腐化し、既に消えた予定地を避けて動く。
**古い協調は、協調しないより悪い。**

## 6. 論評 — この問題設定は何を捉え、何を捉え損ねているか

### 捉えられていること

**「個別最適の合成 ≠ 全体最適」を、極小の系で、定量的に、反証可能な形で再現できている。**
一致率という 1 つの数字が 1.000 に貼り付いたまま成績だけが崩壊するので、
「エージェントが馬鹿だから失敗した」という説明が構造的に排除される。
頭脳・入力・物理を固定して共有度だけを動かせるのは、この問題設定の最大の美点だ。

テトリスという選択も、意図されていた以上に良く働いた。
**共有資源 (列) の奪い合い**があり、**不可逆なコミットメント (lock)** があり、
**締切 (落下) が交渉不能**である。この 3 つが揃っているので、
「待つ」「譲る」「先に決めた者勝ち」といった協調の基本問題が自然に立ち上がる。

### 捉え損ねていること — 率直な批判

**1. 示したことの大半は VLA 固有ではない。**
上の劣化はすべて Dellacherie 探索で起きた。VLA はこの構造に差し込める一部品にすぎず、
「VLA でなければ示せなかったこと」は実はほとんどない。
VLA が本質的に効くはずの部分 — 自然言語で与えた信条 (ペルソナ) が行動を変える、
言語で他者の意図を推測する — は、仕組みは通したが**まだ十分に検証していない**。
mock は所詮「ピクセル経由のノイズ付きオラクル」であって、言語で考えてはいない。

**2. オラクルが固定参照であり、regret の定義が甘い。**
一致率・regret は「確定地形のみに対する最良手」との比較なので、
協調すればするほど下がる。つまり**これは品質の指標として機能していない**。
正しくは N 体同時配置の joint-optimal を厳密探索して参照にすべきで、
それがないと「独裁は本当に最適に近いのか、それとも単に自律よりマシなだけか」が言えない。

**3. A2A の「宣言」は約束ではない。**
守る義務も、破ったときの罰則も、破ったことを検知する仕組みもない。
これは協調ではなく**単なる情報開示**である。交渉・コミットメント・違反検知が入って
初めて A2A と呼ぶに値する。現状は「A2A の下限」を測っているにすぎない。

**4. 独裁の勝利はやや自明で、コストモデルが弱い。**
中央集権が情報的に優位なのは当然。面白いのは「どれだけのコストで」のほうだが、
今回「独裁のほうが推論回数が少ない」という結果が出たのは、
mock が N 体分の出力増を「線形未満 (+35%/体)」と仮定しているから。
実機ではデコードトークン数が効くので、この仮定こそ実測で検証すべき点だ。

**5. ベンチマークとしての厳密さが足りない。**
スコアの重み (0.35/0.30/0.20/0.15) は恣意的で、tier 間でスコアが比較可能かも怪しい。
実機 VLA ではレイテンシが揺れるので再現性がレイテンシ分布に依存する
(replay で判断は固定できるがレイテンシは固定できない — 固定したらもうベンチマークではない)。
現状は「ベンチマークの骨格」であって、較正済みのベンチマークではない。

**6. VLM に不利すぎる可能性がある。**
10x20 の格子で正確な列番号を読む作業は、VLM が最も苦手とする「見る」より「数える」タスクだ。
`--text-board` で盤面のテキスト表現を併せて渡す ablation を用意してあるのは、
**「見えないのか、考えられないのか」**を切り分けるためだが、まだ実機で回していない。
ここで差が出るなら、問題は知覚であって推論ではない。

### さらなる探究の方向

優先度順に:

1. **実機 VLM で T0〜T1 を測る。** `--text-board` の有無で切り分け、
   知覚のボトルネックと推論のボトルネックを分離する。ここが最も情報量が大きい。
2. **joint-optimal オラクルを実装する。** N 体同時配置の厳密探索 (小 N なら全探索可能) を
   参照にして、真の regret を定義する。独裁が最適からどれだけ離れているかが初めて言える。
3. **宣言を約束にする。** 宣言と違う場所に降りたらペナルティ。
   守らないほうが得な状況を作れば、これは即座に交渉ゲームになる。
   部分観測下で「裏切り」を検知できるかが次の問い。
4. **予約と入札。** ゴーストを先着優先の「予約」にする。さらに列の使用権をオークションにかける。
   速い駒ほど締切が近い = 支払意思が高い、という自然な価格が立つ。
5. **協調のスパンを振る。** 5 体中 2 体だけ独裁、残り 3 体は自律。
   「何体まで束ねれば十分か」の飽和点を探す。実務的にはこれが一番効く問いだと思う。
6. **通信帯域とスコアの関係を測る。** ゴースト (視覚) とテキストで差が出なかったのは
   ヒューリスティックがゴーストしか使わないからで、VLA ではテキストが効くはず。
   「何ビット送れば何点上がるか」を測れば、協調の価格が出る。
7. **staleness を織り込む予測制御。** 「自分の判断は N tick 古い」と分かっているなら、
   リードタイムを見込んで先回りできるはず。それを**自然言語でモデルに伝えて改善するか**が
   VLA ならではの問いになる。
8. **敵対的ペルソナ。** 「他を妨害する」信条を 1 体だけ混ぜる。
   部分観測下で妨害者を特定できるか。できるなら何 tick かかるか。
9. **速度を交渉力にする。** 落下速度がばらつくと、速い駒は「先に確定する」権利を持つ。
   これを明示的な優先権にしたとき、遅い駒はどう振る舞うのが最適か。
10. **密度の相転移を探す。** 幅 20〜30 の盤で同時 10 体。
    同時落下数を上げていったとき、成績がなだらかに落ちるのか、ある密度で崩壊するのか。

## 7. 実装メモ

- **テトリス部分**: OSS のエンジンをそのまま使うことは断念した。既存実装はいずれも
  「落下ピースは常に 1 個」を前提に組まれており、同時多ピースは改造ではなく再設計になるため。
  形状・回転・7-bag は SRS の公開仕様どおりに実装している (回転テーブルは手打ちせず
  行列回転から機械生成しているので、「各回転 4 セル」「4-cycle」が構造的に保証される)。
  壁キックは完全な SRS kick table ではなく簡略版で、これは PoC の割り切り。
- **決定性**: seed とアクション列が同じなら実行は完全に再現する。
  mock バックエンドのレイテンシも seed 付き乱数なので、エピソード全体が再現可能。
- **依存**: numpy / Pillow / httpx / pytest のみ。設定は JSON、可視化は ASCII と PNG。
- **テスト**: 152 件。特に重要なのは
  デコード往復同一性 (公平性)、`action_is_legal` と実適用の一致 (反射層の健全性)、
  空中固定が起きないこと (同時落下の lock 規則)、replay の完全再現。
