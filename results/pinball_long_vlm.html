産業制御 × Physical AI — ピンボール／ブロック崩し

同じ盤面の上で 4 つの制御層が別々のクロックで 動いています。下ほど速く決定的、上ほど遅く賢い。上位の判断は必ず古い盤面に対する答えとして降りてくるので、下位はそれを前提に動きます。ジグ（バンパー）に当てると対応する列が 1 個崩れます（工程を 1 回こなす）。ただし叩くたびにジグ自身が摩耗し、耐久度は隠れ状態で打数しか観測できません。耐久が尽きると素通りになりその工程はもう回せなくなるので、シーケンサが救済機を出して直します。使う道具が減っていく、という緊張が中心です。

周期: 毎 tick (50Hz)

周期: 600 tick

ラダーロジック (毎スキャン評価される)

上から順に評価され、上のラングが書いたコイルを下のラングが読めます。だから挙動が完全に読み切れる — ここが AI に置き換えられない理由です。

全体像 — 何が入って、どのコイルが内部に戻り、どれが外へ出ていくか

ラング単体を読めても、系全体の依存はこれを見ないと分かりません。緑の破線＝上のラングが書いたコイルが下のラングの接点として戻る内部フィードバック。黄色の破線枠＝どのラングも読まないコイル、つまりシーケンサへの出力です。ここがラダーとシーケンサの境界になります。

ラング 1 本ずつの回路図

左右の縦線が母線。─┤├─ が a 接点、斜線入りの ─┤/├─ が b 接点 (否定)、右端の ─( )─ が出力コイルです。横に並ぶ接点が直列 (AND)、縦に積まれた枝が並列 (OR)。

ラダーのタイムチャート (ドラレコ)

全 1298 スキャンぶんのビット履歴。○ 青 = 入力接点、◆ 緑 = 出力コイル。帯が立っている区間がその信号 ON。「なぜあの瞬間に修理許可が出た/落ちたのか」を後から追えます。

そのときラダーはどう通電していたか

タイムチャートは「いつ」しか分かりません。同じ瞬間をラダー図に焼き直すと どの経路を電気が通ったか が見えます。緑＝通電、暗い線＝遮断。b 接点が効いて落ちている経路に注目してください。

この 1 回で何が起きたか — 推移と相関

層ごとに別々の表を眺めても、どの助言がどの動きを引き起こしたのかは読めません。同じ横軸に 4 段重ねると、VLM の助言 → シーケンサの状態 → 盤面の事故 → 工程の消化、が縦に揃って読めます。ブロック消化の傾きが寝ている区間の理由は、必ず上の 3 段のどれかにあります。

シーケンサの遷移 (事故対応)

設計上のステートマシンに、この回で実際に通った回数を重ねた図です。暗いままの枠と細い矢印は「設計にはあるが今回は通らなかった」経路。

同じものを構造化テキスト (ST) で

ラダーは接点の直並列には向きますが、状態遷移を読むには向きません。実務でも段取りは FB の ST で書くので、同じ中身を IEC 61131-3 の書き方でも出します。この 2 つは手書きではなく実装から生成しています — ラダーは build_ladder() のラング定義から、シーケンサは Sequencer.step の構文木から抽出しているので、実装を直せばこの ST も追随します（ドキュメントだけ古くなることがない）。

FB_RepairSequencer — 段取りのステートマシン
FUNCTION_BLOCK FB_RepairSequencer
VAR_INPUT
    jig_broken      : BOOL;  (* 素通りのジグがある *)
    repair_permit   : BOOL;  (* ラダーが出す修理許可 *)
    repair_cancel   : BOOL;  (* ラダーが出す取消 *)
    vlm_repair_ok   : BOOL;  (* VLM の助言。命令ではない *)
    drone_done      : BOOL;
    drone_failed    : BOOL;
END_VAR
VAR
    state : E_SeqState := IDLE;
END_VAR

(* 安全に関わる判断はこの FB が持つ。VLM は助言するだけで
   拒否権はこちら側にある、という権限配置をコードで示す。 *)

CASE state OF
    IDLE:  (* 待機 *)
        state := RUN;  (* 起動 *)

    RUN:  (* 通常運転 *)
        IF jig_broken THEN
            state := FAULT;  (* ジグ#N 素通りを検知 *)
        END_IF;

    FAULT:  (* 故障検知 *)
        IF repair_permit AND (NOT repair_cancel) THEN
            state := PLAN;  (* ラダーが修理許可を出した *)
        ELSIF NOT jig_broken THEN
            state := RUN;  (* 故障が解消した *)
        END_IF;

    PLAN:  (* 修理計画 *)
        IF NOT vlm_repair_ok THEN
            state := RUN;  (* VLM が今は危険と助言 → 見送り *)
        ELSIF jig_broken THEN
            state := DISPATCH;  (* 目標ジグ#N を決定 *)
        ELSE
            state := RUN;  (* 対象なし *)
        END_IF;

    DISPATCH:  (* 救済機発進 *)
        state := REPAIR;  (* 救済機発進 *)

    REPAIR:  (* 修理中 *)
        IF drone_failed THEN
            state := ABORT;  (* 修理失敗: N *)
        ELSIF drone_done THEN
            state := RECOVER;  (* 修理完了 *)
        END_IF;

    RECOVER:  (* 復帰 *)
        state := RUN;  (* 定常へ復帰 *)

    ABORT:  (* 中断 *)
        state := RUN;  (* 定常へ復帰 *)

END_CASE;
END_FUNCTION_BLOCK
FB_GateInterlock — ラダーと同じ論理を ST で
FUNCTION_BLOCK FB_GateInterlock
VAR_INPUT
    ball_upper      : BOOL;
    ball_lower      : BOOL;
    stall_timer     : BOOL;
    alt_flag        : BOOL;
    drone_active    : BOOL;
    jig_broken      : BOOL;
    ball_in_danger  : BOOL;
    drone_abort     : BOOL;
END_VAR
VAR_OUTPUT
    hold_gates      : BOOL;
    gate0_open      : BOOL;
    gate1_open      : BOOL;
    gate_inhibit    : BOOL;
    repair_permit   : BOOL;
    repair_cancel   : BOOL;
END_VAR

(* PLC のスキャンと同じく上から順に評価する。
   上の行が書いたコイルを下の行が読めることに意味がある。 *)

    (* R1 上部滞留でゲート閉 — ボールが上段にある間はゲートを開けない *)
    hold_gates := (ball_upper);

    (* R2 滞留タイマでゲート開 — 下段で停滞したらゲート 0 を開けてボールを落とす *)
    gate0_open := (ball_lower AND stall_timer AND NOT hold_gates);

    (* R3 交互ゲート — ゲート 0 と交互に動かして偏りを防ぐ *)
    gate1_open := (gate0_open AND alt_flag);

    (* R4 救済機作動中はゲート禁止 — ドローン飛行中はゲート操作を禁止 (巻き込み防止) *)
    gate_inhibit := (drone_active);

    (* R5 修理許可ラッチ — 故障検知 かつ ボールが危険域外 なら修理許可を保持 *)
    repair_permit := (jig_broken AND NOT ball_in_danger AND NOT drone_active) OR repair_permit;
    (* ↑ 末尾の OR が自己保持 (ラッチ) *)

    (* R6 危険域で許可解除 — 危険域侵入または中断要求で許可を取り消す *)
    repair_cancel := (ball_in_danger) OR (drone_abort);

END_FUNCTION_BLOCK

ST 側の IF / ELSIF / ELSE は Python の分岐と 1 対 1 に対応させてあります。独立した IF に並べ替えると排他性が壊れ、PLAN 状態で 2 つの遷移が同時に成立してしまうためです。

VLM は「今なら修理してよい」と助言するだけで、実際に救済機を出す/止めるの判断は必ずこのステートマシンを通ります。AI 連動でも安全側の権限は組み込みに残す、という形です。
